labubot · Telegram multiusuario

Base de datos

AutoClaroOscuro

labubot.db es lo que se recuerda entre corridas: un SQLite en modo WAL que comparten la api (recibe el webhook de Telegram) y el worker (la corrida horaria). Reemplaza a vistas.txt y a perfil.md: guarda quién usa el bot, cómo configuró sus alertas, la caché de descripciones y qué ofertas ya se evaluaron para cada usuario.

Relaciones

Tres claves foráneas, todas a users(chat_id) y con ON DELETE CASCADE: borrar un usuario borra sus términos, sus palabras bloqueadas y su historial de entregas. La cuarta relación es lógica.

  • users 1 — N user_termsCada usuario tiene cero o más términos de búsqueda. Al aprobarlo se le siembran los DEFAULT_TERMS.
  • users 1 — N user_blocked_wordsCada usuario tiene cero o más palabras que descartan un título. Semilla: DEFAULT_BLOCKED_TITLE_WORDS.
  • users 1 — N deliveriesUna fila por cada (usuario, url) evaluada. Es lo que evita volver a pagarle al LLM la misma oferta para la misma persona.
  • offers 0..1 — N deliveries · por url, sin FKUna oferta bajada se evalúa para varios usuarios. Una entrega importada de vistas.txt no tiene fila en offers, por eso no hay FOREIGN KEY.

Tablas

Una línea por columna. Las fechas son TEXT en ISO 8601 y en UTC (por ejemplo 2026-10-31T14:05:00+00:00).

users

Un usuario por chat privado. Lo crea el primer /start (al admin, migrate.py); lo lee la corrida para saber a quién buscarle ofertas.

ColumnaTipoRestriccionesQué guarda
chat_idINTEGERPKId del chat privado, que en Telegram es el id del usuario. Como es INTEGER PRIMARY KEY, es el rowid y nunca queda NULL.
usernameTEXTNULLEl @usuario. Telegram no lo garantiza: puede faltar.
first_nameTEXTNOT NULLNombre que muestra Telegram; va en el saludo y en la solicitud que le llega al admin.
statusTEXTNOT NULLDEFAULT 'pending'Estado del acceso (UserStatus). Solo active con perfil recibe ofertas.
profileTEXTNOT NULLDEFAULT ''El CV contra el que clasifica el LLM (lo que hoy es perfil.md). '' = todavía no lo cargó.
stateTEXTNOT NULLDEFAULT ''Qué espera el bot del próximo mensaje (ChatState). '' = nada.
created_atTEXTNOT NULLCuándo mandó el primer /start.
approved_atTEXTNULLLa primera vez que pasó a active. NULL mientras está pending o si fue rechazado.

user_terms

Los términos de búsqueda de cada usuario. La corrida le busca a cada usuario los suyos, en orden alfabético; lo que ya buscó otro usuario en esa corrida sale de la caché en memoria.

ColumnaTipoRestriccionesQué guarda
chat_idINTEGERPKFKNOT NULLDueño del término → users(chat_id), ON DELETE CASCADE.
termTEXTPKNOT NULLEl término en minúsculas. La PK compuesta (chat_id, term) impide repetirlo.

user_blocked_words

Las palabras que descartan una oferta por el título, para ese usuario y antes de llamar al LLM.

ColumnaTipoRestriccionesQué guarda
chat_idINTEGERPKFKNOT NULLDueño de la palabra → users(chat_id), ON DELETE CASCADE.
wordTEXTPKNOT NULLEn minúsculas; se busca como substring del título en minúsculas. La PK compuesta impide repetirla.

offers

Caché compartida de descripciones: cada url se baja una sola vez, aunque le interese a varios usuarios.

ColumnaTipoRestriccionesQué guarda
urlTEXTPKUrl de la oferta sin query, la misma clave que hoy usa vistas.txt.
portalTEXTNOT NULLNombre de la clase del portal que la trajo: LinkedIn, Bumeran...
titleTEXTNOT NULLTítulo tal como vino en el listado; es el que va en el mensaje de Telegram.
descriptionTEXTNOT NULLEl detalle bajado con portal.description(url). '' si el portal no lo dio: no se vuelve a pedir y la oferta se saltea.
fetched_atTEXTNOT NULLCuándo se bajó la descripción.

Ojo: en SQLite una PRIMARY KEY que no es INTEGER acepta NULL si no dice NOT NULL (probado sobre este esquema). El contrato no lo agrega; en la práctica la url siempre viene de la oferta.

deliveries

Qué ya se evaluó para cada usuario y si le llegó. Reemplaza a vistas.txt, pero por usuario: la misma url puede ser verde para uno y roja para otro.

ColumnaTipoRestriccionesQué guarda
chat_idINTEGERPKFKNOT NULLPara quién se evaluó → users(chat_id), ON DELETE CASCADE.
urlTEXTPKREFNOT NULLQué oferta. Se cruza con offers(url) sin FOREIGN KEY: las importadas de vistas.txt no tienen fila ahí.
termTEXTNULLLa palabra clave que la trajo para ese usuario: el primero de sus términos (en orden alfabético) cuya búsqueda la trajo o, en los portales sin búsqueda, el primero contenido en el título. Le llega bajo el encabezado 🔎 de esa palabra, aunque salga recién en una corrida posterior. NULL = "Otros portales" o importada de vistas.txt. Es texto copiado, sin FK a user_terms: si el usuario después quita la palabra, la entrega la conserva.
lightTEXTNULLVeredicto del LLM para ese usuario (TrafficLight). NULL = importada de vistas.txt.
classified_atTEXTNOT NULLCuándo se clasificó (o se importó). Se guarda con commit inmediato: lo clasificado no se vuelve a pagar aunque la corrida se corte.
sent_atTEXTNULLCuándo salió el mensaje. NULL si es roja, importada o si todavía no salió: el envío falló, la corrida se cortó entre clasificar y mandar, o Telegram dio 403. Se reintenta en la próxima corrida en que el usuario esté active, dentro del grupo de su term.

Índices

Uno solo declarado a mano; el resto los crea SQLite por las PRIMARY KEY. Los nombres sqlite_autoindex_* son los que aparecen en sqlite_master al correr schema.sql. deliveries.term no lleva índice: nunca se busca por la palabra sola, se agrupa dentro de un usuario, y a sus filas se llega por la PK o por deliveries_pending.

Valores posibles

Tres columnas TEXT que en Python son StrEnum. La base no los restringe con CHECK: los escribe solo el código.

users.status

UserStatus · src/enums/user_status.py

  • pending mandó /start y espera al admin. Solo puede usar /start, que le contesta "⏳ Tu solicitud sigue pendiente."
  • active aprobado. Recibe ofertas cuando profile != ''. El admin entra directo acá.
  • paused usó /pausa o ⏸ Pausar. No entra en la corrida hasta /reanudar o ▶️ Reanudar.
  • rejected el admin lo rechazó. Terminal: /start le responde "No tenés acceso a este bot."
  • blocked Telegram devolvió 403 al mandarle (bloqueó el bot). Vuelve a active con /start (o con cualquier mensaje: si escribe, ya no tiene el bot bloqueado).

users.state

ChatState · src/enums/chat_state.py

  • '' (IDLE) no espera nada. Un texto suelto responde "No entendí...".
  • awaiting_profile después de /perfil o 📄 Perfil: el próximo texto o archivo .md / .txt reemplaza profile.
  • awaiting_terms_add / awaiting_terms_remove después de ➕ Agregar / ➖ Quitar en Términos: el próximo texto, separado por coma, entra o sale de user_terms.
  • awaiting_blocked_add / awaiting_blocked_remove lo mismo con user_blocked_words.
  • Después de procesar el mensaje, con ✖ Cancelar o con cualquier comando, vuelve a ''.

deliveries.light

TrafficLight · src/enums/traffic_light.py

  • green compatible con el perfil. Se manda con 🟢.
  • yellow para revisar a mano. Se manda con 🟡.
  • red no compatible. No se manda: sent_at queda NULL para siempre.
  • NULL importada de vistas.txt en la migración. Ni se clasifica ni se manda.

Estado de una entrega

Lo dicen light y sent_at juntos.

lightsent_atQué significa
green / yellowfechaEnviada.
green / yellowNULLPendiente: el envío falló, la corrida se cortó antes de mandar o el usuario bloqueó el bot (403). Está en deliveries_pending y sale dentro del grupo de su term, junto con las nuevas de ese usuario, en la próxima corrida en que esté active.
redNULLDescartada por el LLM.
NULLNULLImportada de vistas.txt: cuenta como vista y nada más.

Consultas de ejemplo

Las tres que más usa el sistema y una para mirar a mano qué le falta mandar a un usuario. Corridas sobre schema.sql; el plan es la salida de EXPLAIN QUERY PLAN.

Usuarios activos con perfil

Users.active() · paso 1 de la corrida

SELECT *
FROM users
WHERE status = 'active'
  AND profile != ''
ORDER BY created_at;

Plan: SCAN users y USE TEMP B-TREE FOR ORDER BY. Recorre la tabla entera y ordena por orden de alta en memoria; con pocos usuarios no hace falta índice.

Entregas pendientes

Deliveries.pending() · las que no llegaron en corridas anteriores; _run_user se queda con las de su chat_id

SELECT d.chat_id, d.url, d.term, d.light, o.title
FROM deliveries AS d
JOIN users AS u ON u.chat_id = d.chat_id
JOIN offers AS o ON o.url = d.url
WHERE d.sent_at IS NULL
  AND d.light IN ('green', 'yellow')
  AND u.status = 'active'
ORDER BY d.classified_at;

Plan: SEARCH d USING INDEX deliveries_pending, después users por rowid, offers por su PK y USE TEMP B-TREE FOR ORDER BY (ordena en memoria; son pocas filas). El title sale de offers porque el mensaje lo necesita, y el term dice en qué grupo entra cuando le toca a ese usuario.

¿Este usuario ya evaluó esta url?

Deliveries.exists(chat_id, url) · por usuario: elegir las ofertas nuevas

SELECT 1
FROM deliveries
WHERE chat_id = ?
  AND url = ?;

Plan: SEARCH deliveries USING COVERING INDEX sqlite_autoindex_deliveries_1. Si devuelve una fila, esa url no se le vuelve a clasificar.

Pendientes de un usuario, agrupadas por palabra

a mano con sqlite3 labubot.db · lo que tiene pendiente, por grupo

.parameter set :chat_id 123456789
SELECT coalesce(d.term, 'Otros portales') AS keyword,
       sum(d.light = 'green')  AS green,
       sum(d.light = 'yellow') AS yellow
FROM deliveries AS d
WHERE d.chat_id = :chat_id
  AND d.sent_at IS NULL
  AND d.light IN ('green', 'yellow')
GROUP BY d.term
ORDER BY d.term IS NULL, d.term;

Plan: SEARCH d USING INDEX sqlite_autoindex_deliveries_1 (chat_id=?), USE TEMP B-TREE FOR GROUP BY y USE TEMP B-TREE FOR ORDER BY. Entra por la PK y filtra las filas de ese usuario; con unos miles por usuario no hace falta un índice nuevo. El orden es el de los encabezados: palabras en orden alfabético y "Otros portales" (term NULL) al final. Con verdes y amarillas de ejemplo da fastapi 1 0, python 1 1, Otros portales 0 1. Va :chat_id con .parameter set (el número es de ejemplo) y no ?: en el CLI, un ? sin valor vale NULL y la consulta no devuelve nada.

Archivo y DDL

  • Vive en settings.db_path (DB_PATH en el .env, por defecto labubot.db). En modo WAL aparecen al lado labubot.db-wal y labubot.db-shm: son parte de la base, no se borran a mano.
  • journal_mode = WAL queda grabado en el archivo: la api y el worker leen sin bloquearse y escribe uno a la vez.
  • foreign_keys = ON es por conexión: connect() lo activa cada vez. Sin eso, el ON DELETE CASCADE no corre.
  • El esquema de referencia está en schema.sql. En el código va a src/db/schema.sql con IF NOT EXISTS y sin los PRAGMA: connect() los activa y crea las tablas que falten. migrate.py llena la base una sola vez desde perfil.md, vistas.txt y src/config/search.py.
Ver schema.sql 
-- labubot.db: lo que se recuerda entre corridas, compartido por la api (webhook) y el worker.
-- Fechas ISO 8601 en TEXT, UTC.

PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;

CREATE TABLE users (
  chat_id     INTEGER PRIMARY KEY,             -- chat privado = id del usuario de Telegram
  username    TEXT,                            -- @usuario, puede faltar
  first_name  TEXT NOT NULL,
  status      TEXT NOT NULL DEFAULT 'pending', -- UserStatus: pending | active | paused | rejected | blocked
  profile     TEXT NOT NULL DEFAULT '',        -- el CV (lo que hoy es perfil.md); '' = todavía no lo cargó
  state       TEXT NOT NULL DEFAULT '',        -- ChatState: qué espera el bot del próximo mensaje ('' = nada)
  created_at  TEXT NOT NULL,
  approved_at TEXT
);

CREATE TABLE user_terms (
  chat_id INTEGER NOT NULL REFERENCES users(chat_id) ON DELETE CASCADE,
  term    TEXT NOT NULL,                       -- en minúsculas
  PRIMARY KEY (chat_id, term)
);

CREATE TABLE user_blocked_words (
  chat_id INTEGER NOT NULL REFERENCES users(chat_id) ON DELETE CASCADE,
  word    TEXT NOT NULL,                       -- en minúsculas; se busca como substring del título en minúsculas
  PRIMARY KEY (chat_id, word)
);

CREATE TABLE offers (                          -- caché compartida de descripciones: una bajada por url
  url         TEXT PRIMARY KEY,                -- sin query, como hoy
  portal      TEXT NOT NULL,                   -- nombre de la clase: LinkedIn, Bumeran...
  title       TEXT NOT NULL,
  description TEXT NOT NULL,                   -- '' si el portal no la dio (no se vuelve a pedir)
  fetched_at  TEXT NOT NULL
);

CREATE TABLE deliveries (                      -- qué ya se evaluó para cada usuario (reemplaza vistas.txt)
  chat_id       INTEGER NOT NULL REFERENCES users(chat_id) ON DELETE CASCADE,
  url           TEXT NOT NULL,                 -- sin FK a offers: las importadas de vistas.txt no tienen fila en offers
  term          TEXT,                          -- palabra clave que la trajo; NULL = "Otros portales" o importada de vistas.txt
  light         TEXT,                          -- TrafficLight: green | yellow | red; NULL = importada de vistas.txt
  classified_at TEXT NOT NULL,
  sent_at       TEXT,                          -- NULL si es roja, importada, o si el envío falló (se reintenta)
  PRIMARY KEY (chat_id, url)
);

CREATE INDEX deliveries_pending ON deliveries (sent_at) WHERE sent_at IS NULL AND light IN ('green', 'yellow');
